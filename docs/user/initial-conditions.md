# Initial Conditions

MOSE initialises the flow field exclusively from **file-based initial conditions**: a structured file containing both the computational mesh and the cell-centred flow variables for all blocks. There is no inline specification of the flow field inside `input.ini`.

IC files are read via the **[ORION](https://github.com/MarcoGrossi92/ORION)** I/O library. ORION supports multiple formats, all of which MOSE can use:

| Format | Extension | Notes |
|--------|-----------|-------|
| Tecplot ASCII | `.tec` | Human-readable; default in bundled test cases |
| Tecplot Binary | `.szplt` | Compact and fast; requires TecIO |
| VTK | `.vtm`, with its `.vts` block files | Open standard; suitable for large datasets |

!!! info "IC files and ATLAS"
    In the normal Hydra workflow, the IC file is generated by the **ATLAS** pre-processor. ATLAS takes a mesh, a prescribed flow state, and the thermodynamic data as inputs and writes the IC file in the format MOSE expects. If ATLAS is not available, the IC file can be prepared manually as long as it conforms to the expected format (see below).

---

## File Location and Naming

For single-grid cases the IC file is expected at:

```
INPUT/ic.tec          ← Tecplot ASCII (default)
INPUT/ic.szplt        ← Tecplot binary
INPUT/ic.vtm          ← VTK multi-block, with its .vts block files
```

The format is the one of `ic-format` in `[MOSE-IO]`, not the extension of a file. The block files of a `.vtm` are read where it lists them, relative to its own folder, as ORION writes them (`vtk/fieldBlock1.vts` next to `ic.vtm` is `INPUT/vtk/fieldBlock1.vts`); a `.vtm` whose block files are not there is read with them at `INPUT/vtk/field<entry>.vts`, where earlier versions of MOSE looked for them.

A solution written by MOSE can start a new run (`newrun = true`): copy `OUTPUT/field.tec` to `INPUT/ic.tec` (`field.szplt` to `ic.szplt`), or `OUTPUT/field.vtm` to `INPUT/ic.vtm` together with the `OUTPUT/vtk/` folder as `INPUT/vtk/`, and set `ic-format` to the format of the solution. The new run starts from the field of the solution, at time 0 (or iteration 0), with the counters of a new run.

---

## File Format

Regardless of the format, every IC file stores both the **node coordinates** and the **cell-centred flow variables** for each block in a single file — no separate mesh file is used. The variable layout and ordering described below apply to all supported formats.

### Tecplot ASCII (`.tec`)

The most common format for bundled test cases. Human-readable and easy to inspect or generate manually.

### Tecplot Binary (`.szplt`)

Compact binary format produced by TecIO. Recommended for large multi-block cases where ASCII I/O becomes a bottleneck. Requires ORION to be built with TecIO support (`--use-tecio`). The variable list and zone structure are identical to the ASCII format.

### VTK Structured (`.vts` / `.vtm`)

Open-standard XML-based format readable by ParaView and VisIt. Multi-block cases use a `.vtm` (multi-block) container referencing individual `.vts` (structured grid) pieces. Variable names and layout follow the same conventions as the Tecplot formats.

## Required Variables

Every IC file must contain the same set of variables:

| Variable | Description | Units |
|----------|-------------|-------|
| $x,\, y,\, z$ | Node coordinates | m |
| $\rho(i)$ | Partial density of the i-species | kg/m³ |
| $u,\, v,\, w$ | Velocity components | m/s |
| $p$ | Pressure | Pa |


If Spalart-Allmaras turbulence model is used, the IC file must also include:  

| Variable | Description | Units |
|----------|-------------|-------|
| $\rho\tilde{\nu}$ (`rhoNuTilde`) | Spalart-Allmaras working variable times density | kg/(m·s) |

If $k-\omega$ or SST turbulence model is used, the IC file must also include:  

| Variable | Description | Units |
|----------|-------------|-------|
| $\rho k$ (`rhoK`) | Turbulent kinetic energy times density | kg/(m·s²) |
| $\rho\omega$ (`rhoOmega`) | Specific dissipation rate times density | kg/(m³·s) |

The turbulence variables are always the density-weighted ones MOSE advances, in the
IC file as in the restart and solution files, under the names `rhoNuTilde`,
`rhoK`, `rhoOmega` ($\rho\tilde\nu$ is the variable the Spalart-Allmaras model
transports, not the eddy viscosity $\mu_t$, which MOSE writes as `mut`). ATLAS ICB
writes them from either the specific keys `nuTilde`, `k`, `omega` (multiplied by the
density of each cell) or the density-weighted keys `rhoNuTilde`, `rhoK`, `rhoOmega`
(written as given). MOSE reads the variables by position. When the file carries their names
(ASCII Tecplot), it checks the turbulence names: the earlier names of the same
variables (`mi_t`, `mi_tilde`, and `kappa` with its `omega`) are accepted, and any
other name, such as the specific `nuTilde` or `k`, or the eddy viscosity `mut`,
stops the run.

Every value that MOSE takes from the file must be finite: the coordinates of the
nodes and the variables of the cells that it reads by position (the variables after
them, such as the `T` that MOSE writes in its solutions, are not used). A NaN or an
infinity stops the run at setup, in every build, with exit code 1 and the place of
the value, for example

```
 [ERROR] INPUT/ic.tec holds a value that is not finite (NaN or infinity): variable 2 (u) of block 1, cell i, j, k = 50, 1, 1
```

the variable by its position after the coordinates, with its name when the reader
gives the names (Tecplot ASCII), or the coordinate (`x`, `y`, `z`) of a node, whose
indices start from 0. The same holds for the solution that a restart reads; with MPI
every rank stops, also when one rank alone holds the value.

## Restart

When resuming from a previous run (`newrun = false` in `input.ini`), MOSE reads the initial condition from the latest solution file in `OUTPUT/` instead of from `INPUT/`: `OUTPUT/field.*`, written at the end of a run, or else the highest-numbered `OUTPUT/field<N>.*` (`sol-overwrite = false`). The file is read through ORION, in the `sol-format` format. The flow field is restored, with the physical time of a time-accurate run and the global iteration count of a steady run: from a vtk solution, `CYCLE`, or `|TIME|` when the file holds no `CYCLE`; from a Tecplot solution, the magnitude of `SOLUTIONTIME`.

A steady run writes its Tecplot solutions at a negative `SOLUTIONTIME`, minus the global iteration count, in zones without `STRANDID` (static zones), and a time-accurate run at its physical time, with the zone of block *b* in strand *b* (`STRANDID` = *b*), so that Tecplot follows each block through the solutions of the run. A restart from Tecplot reads a negative `SOLUTIONTIME` as a steady solution, whose global iteration count is its magnitude; in a `.szplt` file it is the solution time of the zones (the data set auxiliary data `Time` holds the magnitude only). Tecplot solutions written by earlier versions of MOSE hold the count of a steady run as a positive `SOLUTIONTIME`, with `STRANDID = 0`: a steady restart goes on from them as before, but a time-accurate restart takes them for a solution at time t = count. To start a transient from such a solution, use it as the initial condition (`INPUT/ic.tec`, `newrun = true`), which starts at t = 0.

A solution that holds no time, a vtk file without `TIME` or a Tecplot ASCII file without `SOLUTIONTIME`, cannot be restarted from, since a restart goes on from the time of its solution: the run stops at setup with a message. To start a run from such a solution, use it as the initial condition (`INPUT/ic.*`, `newrun = true`).

If the run went on after the solution the restart reads (it stopped without writing `field.*`, and the restart reads the last `field<N>`), `residual-history.dat`, the probe files and, with the rotating frame, `torque.dat` still hold the rows written after that solution. A restart from a solution with its counters (below) drops those rows first, the rows of later iterations and the time-based probe rows of later times, and then appends its own, so the files go on as those of the uninterrupted run; a last row cut in the middle (a file cut by hand) is dropped too, and a file that does not end with a newline gets one. With any other solution the rows stay and the restart appends its rows after them: remove them before restarting, and leave a newline at the end of the file.

### Exact restart

Every solution stores the values of its cells so that a restart reads back the 64-bit values written: the binary formats (`vtk raw`, `tecplot binary`) store their bits, and the text formats (`vtk ascii`, `tecplot ascii`) write 17 significant digits, the fewest that give back every 64-bit value (a 64-bit real has a 53-bit significand, and the decimal numbers of n digits are closer together than the reals everywhere when 10^(n−1) > 2^53, that is n ≥ 17). The field solution also stores the counters that decide what the run does and writes next, with the same names in every format: as field data of the `.vts` files of a vtk solution, as data set auxiliary data of a Tecplot solution (`DATASETAUXDATA` records after the zones of a `.tec` file):

| Item | Content |
|------|---------|
| time | Physical time; in a steady run minus the global iteration count (`CYCLE`), as in the wall and diagnostic outputs: `TIME` in vtk, the `SOLUTIONTIME` of the zones in Tecplot |
| `CYCLE` | Global iteration count, over all grid levels: first column of `residual-history.dat`, probe rows with `diter` |
| `MOSE_ITERATION` | Iteration count of the grid level of the solution: CFL ramp (`cfl-rise-threshold`), `sol-diter`, `res-diter` |
| `MOSE_OUTPUT_NUMBER` | Number of the last numbered solution (`sol-overwrite = false`) |
| `MOSE_GRID_LEVEL` | Grid level being solved (multigrid sequence) |
| `MOSE_LAST_OUTPUT_TIME` | Time of the last time-based solution (`sol-dtime`) |
| `MOSE_RES_REFERENCE` | Density residual of the first iteration of the grid level: the unit of `res-threshold` (steady runs) |

A restart from such a solution goes on as the uninterrupted run would: within the limits below, the run split in two parts writes the same files as the run in one go, byte for byte, numbered solutions, `residual-history.dat` and probe files included.

Why the run is the same: an iteration of MOSE computes the next state from the primitive variables of every cell, the physical time, the counters of the table above and the time counter of each probe. Everything else it uses (ghost cells, shock sensor, reference velocity of the preconditioning (but see its smoothing below), stiffness of the turbulence sources, time steps, fluxes and residuals) is computed again from these at every stage or step, and the boundary data from the input and the time. A solution holds the primitive variables with all their bits (64-bit values written and read back as they are), the time and the counters; the restart sets the time counter of each probe from the time and drops the rows of `residual-history.dat` and of the probe files written after the solution (below). The restarted run therefore starts from the state of the uninterrupted run and, with the same executable and the same numbers of MPI ranks and OpenMP threads, repeats the same operations and writes the same bits. The limits below are the cases in which part of that state is not in the solution, or in which the uninterrupted run writes something that the solution does not record. The tests `Restart`, `Restart`/`RestartCounters` and `MPIRestart` check it on steady, time-accurate and multigrid runs, with probes, on one and two ranks, in every format (`Restart`/`RestartCounters`; `tecplot binary` when MOSE is built with TecIO).

The counters are taken only from a solution written by a run of the same kind, steady or time-accurate (a steady run writes its solutions at a negative time, minus the global iteration count; the vtk files written before at `TIME` = −1 are steady too). A time-accurate restart from a steady solution starts a new transient at t = 0, with the counters of a new run.

Time-based probe rows (`dtime`) fall on the multiples of `dtime`. A restart that goes on in time writes next the row of the first multiple its time has not reached, whatever the format of the solution; a transient started from a steady solution starts again from the first one.

### Limits

- **Solutions written by earlier versions of MOSE.** A Tecplot solution held no counters, and a vtk solution may lack some (`MOSE_RES_REFERENCE`, below): from a solution without the counters the restart restores the field, the time or the global iteration count, and starts the other counters as a new run does. The CFL ramp starts again, `sol-diter` counts from the restart, the numbered solutions start again from `field1` (replacing those of the first part) and a multigrid sequence starts again from the coarsest level. Text files written with 15 significant digits do not give back every 64-bit value either: the restarted run is then close to the uninterrupted one, not identical.
- **Solutions without `MOSE_RES_REFERENCE`.** A solution written before MOSE stored that counter does not hold the density residual of the first iteration: a steady restart from it measures `res-threshold` from the residual of its own first iteration, as a new run, and says so with a warning. When the residual has already fallen, the restart asks for a further fall by `res-threshold`, which can lie below the round-off of the run: it may then end only at `iter-threshold`. To end about where the uninterrupted run would, set `res-threshold` to ε R₁/Rₙ, with ε the threshold of the first part and R₁, Rₙ the density residuals of `residual-history.dat` at the first iteration and at the iteration of the solution.
- **A run that ends on an output iteration.** The last iteration of a run writes the final solution `field.*` (with `wall.*` and `diagnostic.*`) and its row of `residual-history.dat`, but not the numbered or time-based solution, nor the probe rows, that fall due there. A restart from it does not write them either: the following numbered solutions get a number one lower, a time-based solution due there is written at the first iteration after the restart (and the next ones shift with it), and the probe rows due there are missing. End the first part between two outputs and two probe rows.
- **Time-based probe rows.** The uninterrupted run writes at most one time-based row per probe and per step: when a step passes a multiple of `dtime` without writing its row (a step longer than `dtime`, or a step that writes a `diter` row), the run writes the missed rows later, one per step, while a restart writes next the row of the first multiple its time has not reached. The probe files of a restart are those of the run in one go only when no step passes a multiple of `dtime` without writing its row.
- **Probe variables changed before the restart.** To drop the rows written after the solution, the restart counts the values of each probe row with the `variables` of its own input (a row can take more than one line): if the variables of a probe changed, the rows of its file are not those the restart counts, and it may keep or drop the wrong ones.
- **Multigrid.** A run ends on the finest grid level, where `field` and `field<N>` are written: from a solution with its counters, the restart goes on on the finest level, without solving the coarser ones again. A solution written while a coarser level was being solved (`field-prolongated`, prolongated to the finest level, and `field-level<L>`, on level *L*, both with the time of their iteration) is not read by a restart. Renamed `field` by hand, it goes on on its grid level, from iteration 0 of that level and from the solution restricted again from the finest level, which differs from the solution of that level (restriction after prolongation does not give it back): the run does not reproduce the uninterrupted one.
- **`res-diter` greater than 1, steady runs.** The first iteration of a restart computes the density residual, which the uninterrupted run computes only every `res-diter` iterations: the rows of `residual-history.dat` are the same, but up to the next multiple the convergence test (`res-threshold`) uses that residual, where the uninterrupted run uses the one of the last multiple. When that residual meets the test there, the two runs stop at different iterations.
- **Preconditioning.** The reference velocity Ur is recomputed from the restored solution. With the rotation–curvature correction of the SST model it would also need the velocity gradient of the last stage, which the solution does not hold; `turbulence` does not accept that combination today.
- **Smoothing of the reference velocity (`preconditioning-Ur-smooth` > 0) with block connections.** During a run, the smoothing at the end of a stage takes, in the ghost cells of a block connection, the Ur of the neighbouring block copied at the start of the stage, not yet updated. The solution does not hold it: in the smoothing that prepares the first step after the restart, the Ur of the connection ghost cells is zero, so that step can differ next to the connections. With the default, 0, there is no smoothing.
